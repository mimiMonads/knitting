# Quick comparison with iceoryx2 — 2026-10-22

The C++ Knitting buffer IPC led on small-message throughput in this quick local comparison. The two implementations were effectively tied at 1 MiB. These results compare specific native API paths and settings, not every iceoryx use case or a standalone synchronization primitive.

| Payload | Calls/batch | Knitting calls/s | iceoryx2 calls/s | Knitting / iceoryx2 |
| --- | ---: | ---: | ---: | ---: |
| 64 B | 1 | 3,121,730 | 1,082,205 | 2.88× |
| 64 B | 32 | 11,041,200 | 2,316,049 | 4.77× |
| 4 KiB | 1 | 935,856 | 626,339 | 1.49× |
| 4 KiB | 32 | 1,522,350 | 1,028,126 | 1.48× |
| 1 MiB | 1 | 5,984 | 5,924 | 1.01× |
| 1 MiB | 32 | 5,083 | 5,035 | 1.01× |

Single 64 B calls had p50 round-trip latency of **0.281 µs** for Knitting and **0.871 µs** for iceoryx2. At 1 MiB the throughput gap was about 1%, too small to treat as a meaningful advantage from three short runs.

## Method

- iceoryx2 **0.10.0**, pinned in the included Cargo manifest/lockfile. This is the current implementation linked from [iceoryx.io](https://iceoryx.io/), using its native Rust API. Knitting uses the actual modular C++ implementation in `ipc/`.
- Same machine: AMD Ryzen 7 4700U, Linux 6.5.0-44 x86_64, CPUs 0 and 1 pinned and verified. Rust 1.93.0 release optimization and GCC 13.2.0 `-O3`, no LTO.
- Separate processes and busy polling on both sides. Knitting uses its two directional SPSC lanes. iceoryx2 uses two publish/subscribe services, one for requests and one for replies; it does **not** use the native request/response service. This matches the topology of the buffer channel.
- iceoryx2: one publisher and one subscriber per direction, buffer size 32, max borrowed samples 32, publisher max loaned samples 32, history 0, safe overflow disabled, initial slice capacity equal to the payload size. Every send checks that exactly one subscriber received it.
- Both allocate/loan shared storage and fill every producer byte inside timing. Both stamp each message, checksum every consumer byte, return a 16-byte reply, validate IDs/checksums, and release buffers. The Rust harness calls the same C++ checksum algorithm/compiler configuration through a small C ABI helper, avoiding a Rust-vs-C++ full-byte checksum comparison.
- Native language/harness and allocator/metadata overhead still differ. The iceoryx path has its normal service/sample machinery; Knitting has a narrower cooperative SPSC contract. This is not evidence that the XOR masks alone cause the difference.
- Setup, discovery, connection establishment, process creation, initial mappings, warmup and cleanup are excluded. The iceoryx server stays alive until the client drains the last reply.
- Three independent runs per configuration, alternating implementation order and rotating workload order. Cases run sequentially; no other benchmark or test job was launched alongside them.
- 36 measured runs, 15,126,063 validated calls; measured durations 0.211–0.269 s, after up to 1,000 warmup batches. Quick descriptive measurements, without confidence intervals.
- Calls/s counts completed request/reply pairs. At 32 calls/batch, latency below measures the whole batch, not an individual call. CPU sums both processes. All summaries are medians of per-run metrics, including p99.

## Reproduce

Requires Python 3, GCC/C++20, Rust/Cargo (Rust >=1.89), and network access for the first Cargo build. It does not install iceoryx system-wide or require a daemon.

```sh
python3 ipc/compare_iceoryx.py --repetitions 3 --seconds 0.25 \
  --output results/ipc-iceoryx-reproduction
```

Use a new output directory. The runner builds both implementations and saves metadata, source hashes/copies, compiler versions, binary hashes, raw results and summary files. Original local captures: `results/ipc-iceoryx-2026-10-22/` (ignored). Base commit: `538a279463f53dfbd25d8269a9ead1ad67da30e0`; comparison files and the IPC were uncommitted.
